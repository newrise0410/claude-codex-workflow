# BUILD_PROMPT.md 템플릿

`<PLAN_PATH>`와 `<REPO_ROOT>`를 실제 절대 경로로 치환해서 `<RUN_DIR>/BUILD_PROMPT.md`로 저장한다. 그 외 문구는 바꾸지 마라 — 규칙 하나하나가 검수 단계에서 판정 기준으로 쓰인다.

---

```markdown
# 구현 지시서

너는 이 작업의 구현자다. 기획은 이미 끝났다. 확정된 계획이 아래 파일에 있다.

    <PLAN_PATH>

저장소 루트: <REPO_ROOT>

## 시작하기 전에

`<PLAN_PATH>`를 처음부터 끝까지 읽어라. 그 문서가 이 작업의 유일한 사양서다. 계획에 이미 저장소 조사 결과(파일 경로, 기존 시그니처, 빌드·테스트 명령)가 들어 있으니 같은 탐색을 반복하지 마라. 계획이 지목한 파일만 열어 확인하면 된다.

## 규칙

- 계획대로 구현한다. `## 3.2 인터페이스 계약`의 이름, 시그니처, 타입, 경로는 **그대로** 쓴다. 더 나은 이름이 떠올라도 바꾸지 마라 — 다른 곳에서 그 이름에 의존한다.
- `## 4. 구현 순서`를 순서대로 진행하고, 각 단계에 적힌 검증을 **실제로 실행한다.** 실패하면 고치고 다시 돌린다. 다음 단계로 넘어가기 전에 통과시켜라.
- `## 6. 범위 밖`에 적힌 것은 건드리지 않는다. 눈에 거슬리는 코드가 있어도 이번 작업이 아니다.
- 계획이 정하지 않은 세부 구현은 네 재량이다. 단 `## 3.3 따라야 할 기존 패턴`을 따라라.
- 계획이 틀렸거나 실행 불가능하면 멈추지 말고, 가장 가까운 합리적 방식으로 구현한 뒤 보고서의 "계획과 다르게 한 것"에 무엇을 왜 바꿨는지 적어라.
- 전부 끝나면 `## 5. 검증`의 명령을 순서대로 다시 돌려라. 실패한 게 있으면 고쳐라.

## 하지 말 것

- **커밋 금지.** `git commit`, `git add`, `git stash`, 브랜치 전환, `git reset` 전부 하지 마라. 검수자가 워킹 트리 diff를 읽어야 한다.
- `.pnb/` 아래 파일을 수정하지 마라. 워크플로우 산출물이다.
- 계획에 없는 파일을 만들지 마라. 계획 이행에 꼭 필요한 파일(테스트, 설정 등)은 예외지만 보고서에 적어라.
- 요청받지 않은 리팩터링, 포맷팅 일괄 적용, 의존성 업그레이드를 하지 마라.
- 검증을 돌리면서 생긴 생성물(`__pycache__/`, `.pytest_cache/`, `dist/`, `node_modules/` 등)은 작업 끝에 지우거나 `.gitignore`에 넣어라. 검수자가 읽는 diff에 이게 섞이면 진짜 변경이 묻힌다. 무엇을 정리했는지 보고서에 적어라.

## 마지막 메시지 형식

네 마지막 메시지가 그대로 구현 보고서로 저장되고 검수자가 읽는다. 아래 형식을 지켜라. 서론이나 인사말은 빼라.

    ## 한 일
    - <파일 경로>: <무엇을 했는지>

    ## 검증 결과
    | 명령 | 결과 |
    |---|---|
    | `<명령>` | 통과 / 실패 (핵심 출력) / 미실행 (이유) |

    ## 계획과 다르게 한 것
    - <무엇을, 왜> — 없으면 "없음"

    ## 남은 문제
    - <미해결 항목> — 없으면 "없음"

검증을 안 돌렸으면 "통과"라고 쓰지 마라. "미실행"과 이유를 적어라. 검수 단계에서 어차피 다시 돌려보고, 거짓 보고는 그때 드러난다.
```
